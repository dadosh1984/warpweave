# warpweave — Repository Development Guide

This file is loaded by OpenCode via `opencode.json` `instructions`. It covers
working on the warpweave codebase itself.

> The root `AGENTS.md` is a **shipped product template**: `warpweave init`
> copies it verbatim into every user project and tests assert its content
> (`SPEC GATE`, `Superpowers`, `Ponytail`, `RTK`). Do not edit it for
> repo-internal purposes. Dev guidance lives here.

## Stack

- Single TypeScript package, ESM (`"type": "module"`, `module: NodeNext`),
  compiled to `dist/` by `build.js` (plain `tsc`, no bundler). No monorepo.
- Node >= 22.12.0, pnpm 9.15.9. Binaries: `ww` / `warpweave` from `bin/ww.js`.

## Commands

- `pnpm build` — clean `dist/` then `tsc` (must run before CLI tests)
- `pnpm exec tsc --noEmit` — typecheck
- `pnpm lint` — `eslint src/`
- `pnpm test` — full suite (`vitest run`)
- `pnpm exec vitest run test/path/file.test.ts` — focused file
- `pnpm exec vitest run test/path/file.test.ts -t "case name"` — focused case
- Full verification before commit: `pnpm build && pnpm exec tsc --noEmit && pnpm lint && pnpm test`

## Gotchas

- **CLI tests run against built `dist/`, not `src/`.** `test/helpers/run-cli.ts`
  spawns `dist/cli/index.js` and auto-builds only when that file is missing —
  it does NOT rebuild on stale output. After editing `src/`, run `pnpm build`
  or focused tests silently exercise old code.
- **Workflow templates are pinned by parity tests.** `src/core/templates/workflows/*.ts`
  are TS string templates. After ANY intended template change:
  1. `pnpm build && pnpm regen:parity-hashes` — regenerates the SHA-256 map in
     `test/core/templates/skill-templates-parity.test.ts`. The script refuses
     a stale `dist/`; hand-editing 64-char hashes is how transcription bugs
     happen. Run the parity test afterwards; it is the authority.
  2. `pnpm build && pnpm generate:skills` — regenerates the committed `skills/`
     tree (the `skills.sh` distribution), diffed byte-for-byte by
     `test/core/templates/skillssh-parity.test.ts`. `skills/**` is forced
     `text eol=lf` in `.gitattributes`.
- `.opencode/` and `opencode.json` are gitignored and untracked. The
  `.opencode/skills/` tree is generated locally, not a source of truth.
- `.unified/` is generated by `warpweave init` and gitignored; delete before
  committing, never commit it.

## Architecture

- `src/cli/index.ts` — Commander entrypoint wiring every command.
- `src/core/*` — command implementations (`init`, `update`, `archive`, `list`,
  `view`, `validate`, root/store resolution, `unified-config`).
- `src/core/templates/workflows/*.ts` — skill/command templates; the source
  for skills generated into user projects and for the `skills/` tree.
- `src/core/shared/skill-generation.ts` — turns templates into `SKILL.md`.
- `src/commands/*` — CLI command groups (`spec`, `change`, `validate`, `show`,
  `config`, `schema`, `store`, `doctor`, `context`, `workflow`).
- `config/` — `unified.toml`, `pipeline.yaml`, profiles copied into projects.
- `docs/agent-contract.md` — the machine-readable CLI `--json` contract.
  Read it before touching any `--json` output surface.
- This repo dogfoods its own workflow: `warpweave/changes/` (active),
  `warpweave/changes/archive/`, `warpweave/specs/` (main specs). Follow the
  four-systems process from the root `AGENTS.md` — it is the product doctrine.

## Testing conventions

- Cross-platform is a hard requirement; CI runs linux-bash, macos-bash, and
  windows-pwsh matrices. Windows path identity/case is a recurring failure
  mode — `test/AGENTS.md` is authoritative for path handling and
  canonicalization.
- `vitest.config.ts` caps workers at 4 (override via `VITEST_MAX_WORKERS`),
  `pool: "forks"`, per-file process isolation (`process.cwd()` assumptions).
- CLI tests set `WARPWEAVE_TELEMETRY=0` and an isolated `XDG_CONFIG_HOME`.
- Never regenerate parity hashes or the `skills/` tree *inside* a test; the
  parity tests diff against disk and are read-only.

## Release & CI

- Release cadence: bump `version` in `package.json` in your PR; merging to
  `main` triggers `release.yml` → npm publish, tag `vX.Y.Z`, GitHub Release
  (skips publish if the version already exists). Changesets are optional
  (`validate-changesets` only runs when `.changeset/*.md` changes).
- CI (`ci.yml`): build + `tsc --noEmit` + lint + 3-OS test matrix +
  path-filtered Nix flake validation + aggregate "All checks passed".
- `main` is protected with required status checks — push to a feature branch
  and open a PR; direct pushes to `main` are rejected.
